# Agent-Native Kanban — 振る舞い仕様

## 1. 基本原則

本システムは、人間とAIエージェントが対等な作業主体として参加し、仕事を発見・取得・遂行・引継ぎするための共有作業管理システムである。

- 人間とエージェントは共通の情報モデルと操作体系を利用する。
- エージェントの起動・実行・停止・スケジューリングは管理しない。
- タスクの業務上の進行段階と、実際の作業状態を区別する。
- 作業の責任者と現在の作業者を区別する。
- 誰が何を実行可能かを、他の情報からの曖昧な推測に依存せず判定できる。
- 人間のUIで行える主要操作は、外部APIからも実行できる。

## 2. 主体と組織

### 2.1 主体の独立性

- 組織は人間・エージェントの主体を登録できる。
- エージェントは独立した識別子・認証情報・権限を持つ。
- エージェントは作成者である人間に所有されない。
- 作成者が退職・削除されても、エージェントとその作業履歴は維持される。
- 組織の管理者はエージェントの権限・認証情報・有効性を管理できる。
- エージェントの実行環境やモデルを変更しても、主体としての同一性は維持される。

### 2.2 権限

- 組織・プロジェクト単位で閲覧・作成・変更・管理権限を与えられる。
- 作業の取得、担当変更、レビュー、承認なども権限として区別できる。
- 主体は自分の権限で操作し、他の人間の代理として認証する必要がない。
- 認可されていない情報はAPI・UI・通知を通じて公開されない。

### 2.3 権限の委譲

主体は、自分の認証情報から権限を絞った委譲トークンを発行し、サブエージェントなどの短命な実行者に渡せる。目的は、実行者の誤りや暴走の影響範囲を抑えることである。独立したレビューや承認の保証は目的に含まず、遷移ルールと別の主体の権限で実現する。

- 委譲トークンは新しい主体を作らない。発行した主体の認証情報であり、作業の記録の主体は発行した主体のままとする。
- 委譲は権限を狭めるだけなので、組織管理者権限も追加の権限も必要としない。人間とエージェントは同じ操作で委譲する。
- 委譲の範囲はプロジェクトと権限で指定し、さらに特定のタスクとその子孫に限定できる。タスクを限定した委譲トークンは、範囲外のタスクを読むことも変更することもできない。
- 委譲できるのは、委譲元が持つ範囲だけである。`review` と `approve` は委譲できる。`admin` は委譲できない。
- 実効権限はリクエストごとに判定する。主体の現在の権限と、委譲元をたどった全ての委譲の範囲を全て満たすものだけが有効である。
- 委譲トークンの有効期限は必須で、委譲元の有効期限を超えられない。有効期限の長さに上限は設けない。
- 委譲トークンからの再委譲は、さらに範囲を狭める場合に限り、深さの制限なく行える。
- 委譲元の失効・期限切れ、主体の無効化・削除により、その子孫の委譲トークンも全て無効になる。発行者は自分の委譲トークンを個別に失効できる。
- 委譲トークンは、通常のトークンの発行やパスワードの変更など、委譲の範囲を超える権限の取得に使えない。
- 委譲トークンの発行・失効・拒否は記録する。委譲トークンによる操作の履歴は、どの委譲トークンの操作かを追跡できる。

## 3. プロジェクトとタスク

### 3.1 タスクの管理

利用者はタスクを作成し、以下の情報を管理できる。

- タイトル、説明、目的、完了条件
- 所属プロジェクト、業務プロセス段階
- 責任者、担当者、優先度
- 依存関係、関連タスク、親子関係
- コメント、添付資料、成果物
- 作業状態、作業主体、履歴

タスクは人間にもエージェントにも同じ形で提示される。

### 3.2 業務プロセス

- プロジェクトごとにワークフローと段階を定義できる。
- Kanbanの列は、その段階を表す。
- 段階は自由に命名・構成できる。
- タスクは明示的な操作によって段階を変更できる。
- 段階の変更には権限や遷移条件を設定できる。

**段階は作業状態を意味しない。**

例えば「レビュー」段階にあるタスクは、レビュー待ち・レビュー中・レビュー中断・レビュー作業完了のいずれでもあり得る。

作業の取得・中断・解放によって、段階が暗黙に変更されることはない。

## 4. 作業状態と着手可能性

### 4.1 独立した概念

システムは少なくとも次を区別して表現する。

| 概念 | 意味 |
|---|---|
| 業務段階 | ビジネスプロセス上の現在位置 |
| 責任・割当 | 誰が仕事に責任を負うか |
| 作業準備状態 | 作業可能か、条件待ちか、必要な作業が完了したか |
| 作業占有 | 現在誰がその仕事を引き受けているか |
| 作業活動 | 占有者が作業中・一時停止中など、どの状態を申告しているか |

これらは別の情報として取得・解釈できる。

### 4.2 作業の取得可能性

タスクについて、以下を機械的に判断できる。

- 現在、作業を取得できるか。
- 作業中の主体が存在するか。
- 占有しているが現在は作業していない主体が存在するか。
- 作業できない場合、その理由は何か。
- 自分がその仕事を取得する権限を持つか。

例えば次の状態を区別できる。

| 状況 | 他の主体が取得できるか |
|---|---|
| 着手条件を満たし、占有者がいない | できる |
| Aが取得し、作業している | できない |
| Aが取得しているが、一時停止中 | 原則できない |
| 占有者はいないが、依存作業が未完了 | できない |
| 現段階の必要な作業が完了している | 原則できない |

取得可能性は、業務段階の名称や担当者の有無から推測しない。

また、作業状態はシステムに報告された状態であり、外部プロセスの稼働を常に保証するものではない。

## 5. 作業のライフサイクル

### 5.1 発見

- エージェントは自身にアクセス可能なタスクを検索・列挙できる。
- 自分が取得可能な仕事だけを抽出できる。
- 優先度・期限・依存関係・プロジェクトなどで絞り込める。
- タスクを開くことで、作業に必要な文脈を取得できる。

### 5.2 取得

- 人間またはエージェントは、取得可能な仕事を引き受けられる。
- 取得が成功すると、現在の作業主体として記録される。
- 競合する取得があった場合、複数の主体が同時に排他的な作業権を得ることはない。
- 取得できなかった主体には理由が返される。
- 取得しても責任者や業務段階は変更されない。

### 5.3 作業

- 作業主体は作業開始・中断・再開を表明できる。
- 進捗、判断、問題、成果物を記録できる。
- 他の主体に質問やレビューを依頼できる。
- 作業状態は他の利用者から確認できる。
- 作業主体以外の操作は、その権限と操作内容に応じて制限される。

### 5.4 解放・引継ぎ

- 作業主体は仕事を解放できる。
- 解放後は、着手条件を満たしていれば別の主体が取得できる。
- 作業を特定の主体に引き継げる。
- 引継ぎでは、それまでの成果物・判断・残課題が維持される。
- 管理権限を持つ主体は、作業放棄などの際に占有を解除・移管できる。
- 占有者が変更された後、以前の占有者は古い作業権によって更新できない。

### 5.5 作業完了

- 作業主体は、実施した仕事の完了を報告できる。
- 完了報告には成果と必要な証跡を残せる。
- **作業完了と業務プロセスの進行は別の操作である。**
- 業務段階を進めるか、同じ段階で別の仕事を開始するかは、ワークフロー上の判断に従う。
- 完了した作業は明示的な再開操作なしに再取得可能にならない。

## 6. 協働と依存関係

- タスク間に依存・ブロック関係を設定できる。
- 依存・ブロック関係、関連タスク、親子関係は同一プロジェクト内に限定する。プロジェクト横断の概念・関係の扱いが定まるまでは、横断する関係を作成できない。
- 依存関係が着手条件に影響する場合、その理由を明示できる。
- タスクを分割し、別の主体に独立して割り当てられる。
- 複数の作業を並行して進める場合、それぞれの作業主体と状態を区別できる。
- コメント、質問、レビュー依頼、意思決定をタスクに紐づけて共有できる。
- 引継ぎ先は以前の作業者との会話履歴を持たなくても、記録された作業文脈を取得できる。

### 6.1 共有リソース

組織またはプロジェクトは、テスト環境など同時に利用できる数が限られた共有リソースを持てる。リソースは名前、説明、同時利用数の上限を持ち、上限1は排他、2以上は複数枠として扱う。

- 確保はタスクの作業占有とは別の記録で、理由とともに主体が1枠を使っていることを表す。
- 満杯なら待ち行列に入れず拒否する。待つ主体は変更イベントを購読し、解放を検出して再試行する。
- 期限、リース、自動解放は持たない。実際に使っている資源を期限で二重に割り当てないためである。
- 確保した主体だけが解放できる。管理者は理由を記録して確保を解除できる。
- 主体の無効化・削除、タスクの完了は確保を解放しない。放置された確保は管理者が明示的に解除する。
- 確保中のリソースは削除できず、上限は現在の確保数より下げられない。
- 確保理由はリソースを閲覧できる主体に共有される。秘密情報は記録しない。

## 7. UIとAPI

### 7.1 Web UI

Linearに近い操作体験を提供する。

- プロジェクト一覧、Kanbanボード、タスクリスト、詳細画面
- 検索、絞り込み、並べ替え
- キーボード中心の高速操作
- タスクの作成・編集・移動
- コメント、履歴、関連タスクの閲覧
- 人間とエージェントを区別せずに扱える担当・作業者の表示

**ボード上では業務段階と作業状態を別々に表示する。**

例えば「レビュー」列のカードには、現在の作業者と作業状態が別途表示される。

### 7.2 API

- UIと同等の主要機能を利用できる。
- 認証された主体の権限に応じて操作できる。
- 仕事の検索・取得・状態変更・解放・完了を実行できる。
- 操作の成功・失敗・競合・権限不足を区別できる。
- 変更イベントを購読し、新しい仕事や作業状態の変化を検出できる。
- API利用のためにブラウザ操作や人間ユーザーのセッションを必要としない。

MCPは必要なら提供してよいが、基本的な機能は特定のエージェントSDKに依存しない。

## 8. 履歴と説明可能性

- 重要な操作について、主体・日時・変更内容を記録する。
- 業務段階の変更と作業状態の変更を区別して追跡できる。
- 作業者の変更・引継ぎ・管理者による解除の経緯を確認できる。
- 失敗した操作は理由を理解できる形で返す。
- 作業状態が不明・不整合になった場合、取得可能と安易に判断しない。

## 9. 代表的な受け入れシナリオ

### シナリオA：エージェント同士の協働

1. Agent AとAgent Bが同じプロジェクトを監視する。
2. 両者が取得可能なタスクXを発見する。
3. AがXを取得する。
4. BからはXが占有中と認識できる。
5. BがXを取得しようとすると拒否される。
6. Aが作業を完了し、結果を記録する。
7. Xの業務段階は、必要な遷移が行われるまで変わらない。

### シナリオB：人間への引継ぎ

1. Agent Aが実装作業を進める。
2. Aは判断が必要になり、人間Hに確認を依頼する。
3. Hはタスクの文脈と判断事項を確認する。
4. Hが回答する。
5. Aまたは引継ぎ先のAgent Bが作業を続ける。
6. 過去の経緯はタスクから取得できる。

### シナリオC：レビュー段階

1. タスクXが業務段階「レビュー」に移動する。
2. レビュー作業が取得可能になる。
3. Agent Bがレビューを取得する。
4. Xは「レビュー」段階のまま、Bが作業中と表示される。
5. Bがレビュー結果を記録する。
6. レビュー承認によってXが次の業務段階へ進む。

### シナリオD：エージェントの運用主体変更

1. 組織の管理者HがAgent Aを登録する。
2. Aが継続的にタスクを担当する。
3. Hが退職し、アカウントが削除される。
4. AのID・権限・履歴・担当タスクは維持される。
5. 新しい管理者がAの設定を変更できる。
6. Aの実行システムを交換しても、同じ主体として作業を続けられる。

## 10. 対象外

本システムは次を主要責務としない。

- AIモデルの選択・推論・実行
- エージェントプロセスの起動・停止
- 実行環境のプロビジョニング
- エージェントのスケジューリング
- 会話メモリや推論コンテキストの管理
- コード実行・CI/CDのオーケストレーション

これらは外部システムに委ねる。

本システムが責任を持つのは、**誰が、何を、どの業務段階で、どのような作業状態として扱っているかを、矛盾なく共有・操作できること**である。
